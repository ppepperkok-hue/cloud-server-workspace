# 02 · 操作安全与变更控制

生产环境一切操作以「可回滚」为前提。本文件是执行任何变更前的强制流程。

## 1. 变更分级

| 级别 | 定义 | 要求 |
| --- | --- | --- |
| **低危** | 只读、日志查看、状态查询、非核心配置调整 | 记录即可 |
| **中危** | 重启单服务、常规部署、改单机配置、普通备份 | 先备份/确认回滚 → 变更 → 验证 → 记录 |
| **高危** | 删库、重置、改密、核心服务重启、集群变更、网络/安全组、升级大版本、force push | **必须**：书面回滚方案 + 用户明确批准 + 维护窗口 |

## 2. 变更控制流程（中危及以上强制）

1. **准备**：写清目标、影响范围、前置条件、回滚方案（用 `templates/operation-record.md` 的「计划」段）。
2. **备份/快照**：可回滚的都要留一手；数据库、配置、镜像、代码至少有一种可恢复手段。
3. **批准**：高危必须用户明确批准；中危在 CHANGELOG 里写明理由。
4. **执行**：按 runbook 或脚本执行；能 `--dry-run` 先 dry-run。
5. **验证**：用真实/代表性输入验证结果，记录验证证据；失败立刻回滚。
6. **记录**：追加 `state/CHANGELOG.md`（动作、结果、回滚方式、验证证据）。

## 3. 回滚原则

- 每个高危变更**先有回滚再动手**；回滚方案写在变更前。
- 回滚本身也是一次变更，执行后同样记录。
- 无法回滚的操作（如 `DROP DATABASE` 无备份）**禁止执行**，除非用户书面确认并已知风险。

## 4. 备份与恢复

- 备份脚本统一放 `scripts/backup/`，配置放 `configs/`。
- 备份必须**定期验证可恢复性**（能恢复的备份才叫备份），验证结果记录到 CHANGELOG。
- 恢复操作视为高危变更，走第 2 节流程。

## 5. 红线（违反即严重事故）

- 静默吞错、假装绿灯。
- 生产环境直接改、不记录、不验证。
- 密钥写入代码/日志/文档（见 `03-secrets.md`）。
- 无回滚方案的破坏性操作。
- 覆盖他人正在进行的任务或文件。

## 6. 失败显式化

任何操作失败、脚本报错、验证不过，**必须**：
1. 停止后续步骤，先回滚或止损；
2. 在 CHANGELOG 记录失败详情与影响；
3. 若影响面大，触发 `docs/postmortems/` 复盘流程。
